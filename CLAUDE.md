# Builder

A desktop pagebuilder that runs in recent Chrome only, for professionals who build websites.

## One tree, one copy

There is one working tree, this root, and one copy of the application. No worktrees, no agent branches, no parallel
trees, no code waiting to be merged, no hooks or guards that block an operation. Work is committed on `main` as it
advances; a change that is not finished stays in the working tree, never on another branch.

## The documents

This file holds the rules of work only. What the product is and must do, what is done and missing, the open problems
and the decisions live in one place: **[`docs/PRODUCT.md`](docs/PRODUCT.md)** (versioned, in English). The others:

- `spec/BEHAVIOUR.md` — the behaviour specs, one section per feature, anchored by the feature's id. The manifest
  points at a section (`spec/BEHAVIOUR.md#<id>`) and `manifest:check` fails when a named section is missing.
- `manifest/` — the contract itself. `src/manifest/schema.ts` is its schema; `npm run manifest:check` validates it.
- `docs/FEATURES.md`, `docs/INVENTORY.md`, `docs/inventory.json` — generated by `npm run inventory` from the manifest,
  the source, the spec and the last complete browser run on a clean tree (`docs/feature-results.json`, written by the
  runner). Never edited by hand; `inventory:check` fails while they are out of step.
- `docs/QA-LOG.md` — the history: every change, one commit each, with what the person met and what changed.
- `docs/AUDIT-<date>.md` — dated snapshots of quality, frozen once written.
- `docs/archive/` — superseded documents kept whole, each with a first line saying where its content went.
- `AGENTS.md` — the entry for Codex: it sends Codex here and adds only what is Codex-specific.
- `.memory/` (ignored by git) — the working memory of a session only, never requirements or the plan.

A new requirement, problem or decision goes into `docs/PRODUCT.md` in the same commit as the work it concerns.

## Memory: read it first after a compaction

The working memory is **[`.memory/builder.md`](.memory/builder.md)** (at most 60 lines): where the work stands and what
to continue next. After a context compaction (or at the start of a session), read it, then `docs/PRODUCT.md`
(sections 2–4), then the last rows of `docs/QA-LOG.md`. Rewrite it whole after every commit. The assistant's own memory
index (`~/.claude/projects/C--Codex-Shared-deepseek-builder-6/memory/MEMORY.md`) points at the same file.

The old application (the Pager) is read-only reference material at `../builder-5/reference/`, for behavior only,
never for code. Never write inside it.

## The loop

```
npm run check:fast     # gen:check, manifest:check, inventory:check, typecheck, deps:check, lint, unit (~1 minute)
npm run ui -- <flow>   # drive the real app in Chrome with real gestures, a photo per step
npm run e2e:affected   # the browser tests of what changed (the features a change reaches)
npm run e2e -- <spec>  # the tests of what the block built (at the end of a block)
npm run e2e            # the complete suite, once, when the whole application is ready
npm run e2e:tooth      # the tooth proof
npm run e2e:diagnose   # the failed tests again, with their trace
npm run inventory      # regenerate the inventory and docs/FEATURES.md
```

What each command verifies, and the other tools (perf, parity, Companion, module removal), are in `docs/PRODUCT.md`
section 6.

- No suite runs between steps. Every feature is written with its basic test, and every screen is checked with
  Playwright on the installed Chrome (`channel: 'chrome'`) — never the embedded preview pane, which cannot press
  modified keys, drag or read what the app stored. `npm run ui` is that check: real gestures one at a time, a
  screenshot per step into `.cache/logs/ui-<flow>-<time>/`, and a failure on any console error, incident or unmet
  expectation.
- **At the end of a block: the tests of what the block built.** The complete suite runs once, at the end.
- Never edit, skip or loosen a test or a scenario to make it pass; if one looks wrong, stop and say why. Never fake a
  result.
- The complete output of every command you claim goes to `.cache/logs/`; in the chat, the exit code, the failing test
  names and the last lines.

## The contract is the manifest

- A change of behaviour starts in the manifest (and in `spec/BEHAVIOUR.md` when it needs words), in the same commit
  as the code, and `npm run manifest:check` stays green.
- The UI registers doors only from the manifest: every button, menu item, field, handle and shortcut is generated
  from a door in `manifest/commands/*.json`. A door whose feature is not registered is drawn disabled with "not
  available yet" (`src/editor/doors/door.test.tsx` proves the drawing); the context menu draws only what applies.
- A door's adapter data is read from the manifest, never re-listed in code. Status comes only from the runner: a
  feature passes when every scenario passes through every door it names. Never write a status or `passes` field.
- The owner of a concept is the module that registers its commands; the inventory names it. A second implementation
  of a concept that has an owner is a defect.

## Architecture and stack

- `src/core/` is the document core in plain TypeScript (no React, no DOM; its ports are injected), `src/editor/` the
  React editor, `src/app/` the wiring, `src/manifest/` the contract's reader, `src/generated/` written by `npm run
  gen` alone.
- One store. State changes only through `dispatch(command)`; handlers are pure and return JSON patches, applied in
  `src/core/store/store.ts` with the tree's invariants owned by `src/core/document/tree.ts`. No document or selection
  state in `useState` or `useRef`.
- A commit the validator refuses after a command produced patches is a bug: nothing of the change is published, the
  status bar says the change was refused (never a silent failure), the incident feed records it, and development and
  tests throw. Predictable invalid operations are refused before any patch exists.
- The document JSON is the source of truth, never the DOM; the page renders in an iframe scaled with CSS `zoom`.
- npm (never pnpm), TypeScript strict, Vite, Vitest, Playwright with `channel: 'chrome'`. Colors, spacing, type,
  radii and shadows come only from the tokens (`src/ui/tokens.css`, generated). UI text only through the i18n
  catalogues (en is the source, pt-BR ships). Code, comments, docs, file names and commits in English; file names in
  kebab-case; tools in TypeScript (the exceptions are listed in `docs/PRODUCT.md` section 7).
- Export: a ZIP with HTML plus a separate CSS file, BEM classes, no inline styles. The dev server port comes from
  `PORT`.
