# Builder

A desktop pagebuilder for professionals who build websites; it runs in recent Chrome only. This file holds the rules
of work only. What the product is and must do, what is done and missing, the open problems and the decisions live in
**[`docs/PRODUCT.md`](docs/PRODUCT.md)**; a new requirement, problem or decision goes there in the same commit as the
work it concerns.

## One tree, one copy

One working tree (this root), branch `main`, one copy of the application: no worktrees, branches, parallel trees or
code waiting to be merged, no git hooks. An unfinished change stays in the working tree. The old application (the
Pager, `../builder-5/reference/`) is read-only reference for behaviour, never for code.

## The documents

- `spec/BEHAVIOUR.md` — one behaviour section per feature, anchored by its id; `manifest:check` fails on a missing one.
- `manifest/` — the contract; `src/manifest/schema.ts` is its schema.
- `docs/FEATURES.md`, `docs/INVENTORY.md`, `docs/inventory.json` — generated by `npm run inventory` (from the
  manifest, the source, the spec and `docs/feature-results.json`, written by a complete browser run on a clean tree).
  Never edited by hand.
- `docs/QA-LOG.md` — one row per change, one change per commit.
- `.memory/` (ignored by git) — session memory only. Read **`.memory/builder.md`** (at most 60 lines, rewritten after
  every commit) at the start of a session and after a compaction, then `docs/PRODUCT.md` sections 2–4 and the last rows
  of `docs/QA-LOG.md`.

## The loop

```
npm run check:fast     # gen:check, manifest:check, inventory:check, typecheck, deps:check, lint, unit (~1 minute)
npm run ui -- <flow>   # the real app in Chrome with real gestures, a photo per step
npm run e2e:affected   # the browser tests of what changed
npm run e2e -- <spec>  # the tests of what a block built
npm run e2e            # the complete suite, once, when the whole application is ready
npm run e2e:tooth      # the tooth proof
npm run e2e:diagnose   # the failed tests again, with their trace
npm run inventory      # regenerate the inventory and docs/FEATURES.md
```

The other tools (perf, parity, journey, capture corpus, Companion, module removal) are in `docs/PRODUCT.md` section 6.

- Every feature comes with its basic test; every screen is checked with Playwright on the installed Chrome
  (`channel: 'chrome'`, `npm run ui`), never the embedded preview pane, and the photos are looked at.
- No suite runs between steps; at the end of a block, the tests of what it built; the complete suite once, at the end.
  One Playwright run at a time.
- Never edit, skip or loosen a test or a scenario to make it pass; if one looks wrong, stop and say why. Never fake a
  result. The complete output of every command claimed goes to `.cache/logs/`.

## The contract is the manifest

- A change of behaviour starts in the manifest (and `spec/BEHAVIOUR.md` when it needs words), in the same commit as
  the code, with `npm run manifest:check` green.
- Every button, menu item, field, handle and shortcut is a door of `manifest/commands/*.json`; a door whose feature is
  not registered is drawn disabled with "not available yet"; the context menu draws only what applies. Adapter data is
  read from the manifest, never re-listed in code.
- Status comes only from the runner: a feature passes when every scenario passes through every door it names. Never
  write a status or `passes` field.
- The owner of a concept is the module that registers its commands; a second implementation of it is a defect.

## Architecture and stack

- `src/core/` the document core in plain TypeScript (no React, no DOM; ports injected), `src/editor/` the React
  editor, `src/app/` the wiring, `src/manifest/` the contract's reader, `src/generated/` written by `npm run gen` alone.
- One store: state changes only through `dispatch(command)`; handlers are pure and return JSON patches, applied in
  `src/core/store/store.ts`, the tree's invariants owned by `src/core/document/tree.ts`. No document or selection state
  in `useState` or `useRef`.
- A commit the validator refuses after a command produced patches is a bug: nothing is published, the status bar says
  it was refused, the incident feed records it, development and tests throw. Predictable invalid operations are refused
  before any patch.
- The document JSON is the source of truth, never the DOM; the page renders in an iframe scaled with CSS `zoom`.
- npm (never pnpm), TypeScript strict, Vite, Vitest, Playwright. Colours, spacing, type, radii and shadows only from
  the tokens (`src/ui/tokens.css`, generated); UI text only through the i18n catalogues (en the source, pt-BR ships).
- Code, comments, docs and file names in English, file names in kebab-case, tools in TypeScript (exceptions:
  `docs/PRODUCT.md` section 7); commit messages in Brazilian Portuguese (DEC-63).
- Export: a ZIP with HTML plus a separate CSS file, BEM classes, no inline styles. The dev server port comes from `PORT`.

## Commits

The repository is **https://github.com/designathan1988/app-pagebuilder-v4.git** (`origin`), always: every change is
committed and pushed there, with `npm run gate -- .cache/scratch/msg.txt <tag> <paths...>`. The gate writes the
previous QA-LOG row's hash, runs `check:fast` on exactly the paths named, commits on `main` and pushes to `origin`.
Never `--no-verify`, `--amend` or a force push.
